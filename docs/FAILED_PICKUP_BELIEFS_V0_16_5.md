# Hearthbound v0.16.5 — Failure-aware pickup beliefs and explicit scout re-observation

## Evidence driving this work

In the fully passing v0.16.4 matched Forge pilot ([PR #188](https://github.com/dylandlr/hearthbound/pull/188)), both scripted and simulator-trained frozen MLP agents:
- delivered one actual wheat from a freshly reported source in seed 3101;
- selected the same chest after it was emptied without telling the executor in seed 3102;
- attempted the now-empty pickup and physically paused, with **zero** delivery credit.

Both achieved 1/2 real deliveries and mean pre-registered utility 0.25. **No neural advantage was demonstrated.** The gap is not simply model size: neither agent had a job-linked feedback path from attempted extraction into its recipient-scoped beliefs.

## What this version changes

A physical error now has an explicit *meaning*: if the actual Minecraft motor reaches the source and `extractWheat()` returns no item, it records a negative result on the **actual executor's persistent villager NBT** before pausing. The event binds real world UUID, executor UUID, job UUID, assigned and failed server ticks, source coordinates, and selected pre-task report ID. It has the evidence origin `REAL_SOURCE_EXTRACTION_RETURNED_EMPTY`.

**This is NOT proof that the chest was empty.** Capability failures can also return an empty extracted stack. It is evidence that a particular physical attempt yielded zero cargo; the test's operator checks the real chest inventory separately.

Events are not generated by pathfinding distance, timeout, source-claim conflict, full destination, missing chunk or inferred hidden world state. No world inventory is read when writing the event.

The next read of the executor's own `CitizenKnowledgeExchange.decisionReport` checks any verified negative outcomes for that source and rejects an earlier report, including a redelivered report with a later delivery timestamp. The original report remains in NBT as history. It can become eligible again only if a different citizen physically observes the source **after** the failed extraction and explicitly delivers qualifying new source evidence.

Both existing scripted and frozen-MLP policy paths automatically receive this filter through their established shared report accessor; the motor and choice policies do not receive omniscient inventory data.

### Bounded persistence and failure modes

Up to 32 job-linked negative events can be stored in the executor's NBT. Invalid schema or saturated storage blocks report-based choice instead of deleting evidence to permit stale replay. Reattempting the same job does not mint a new negative tick or resurrect its previous report.

This is ordinary Minecraft **villager persistent NBT**, not an fsync evidence journal. The additional **crash/disk rollback guarantee has not been demonstrated here**; a separate deliberate restart/rollback test remains necessary before claiming that failed-pickup memories survive unexpected process death without loss.

## Explicit re-observation

Two new permission-2 operator commands:

```text
/hearthbound-pickup-belief <executor> <source>
/hearthbound-reobserve-request <executor> <source>
```

The first reads only the citizen's recorded failed extraction, never the live chest. The second creates a citizen-owned `AWAITING_SCOUT_DIRECT_OBSERVATION` request, but **does not** move or teleport a scout, inspect inventory or fabricate communication. A marked physical scout must still perform the existing `hearthbound citizen_observe` and `hearthbound-share-direct` action paths, with the normal distance/freshness and citizen-identity checks.

The request becomes `FULFILLED_BY_NEW_DIRECT_REPORT` only when the source is observed after the failed tick by an independent scout and delivered to the requesting recipient. A replay of the original report cannot satisfy it.

The paused no-cargo task still requires the existing, safe operator `sable haul-cancel` to release the old job's source claim; the failed history remains separately recorded. This milestone does **not** silently auto-cancel cargo-bearing tasks or infer successful completion.

## Real Forge acceptance

The dedicated `real-failed-pickup-reobservation.yml` starts a disposable Forge server with A=3 wheat, B=1 wheat, destination empty, and two distinct villagers:

1. Scout directly observes A and B, then shares both to the executor.
2. Operator empties A without sharing the change. The scripted baseline now selects A from stale secondhand knowledge and creates an actual job.
3. The real executor physically attempts extraction; the motor reports `No wheat available`. Its job-linked negative event is inspected, with `source_empty_verified=false`.
4. Before further communication, the same scripted report policy must reject A and choose B. An early re-observation request without a real failed job is rejected.
5. Request new source observation. Replaying the old A report yields a duplicate and does not satisfy the request.
6. Safely cancel the original unpicked task. Scout physically reobserves A=0, shares the new direct observation, and the original request is marked fulfilled.
7. The executor replans to B, creates a distinct hauling job, physically delivers B's one wheat, and the operator checks **A: 0 → 0, B: 1 → 0, destination: 0 → 1** on actual Minecraft block inventories.
8. The first failed job remains in the citizen's negative history; it never becomes a completion or a research reward.

Unit tests additionally validate failure identity, timestamp ordering, reused reports from other senders, strict re-observation freshness, wrong world/executor rejection, and distinction between real extraction versus inferred navigation failure.

## What this does not prove

This is still **operator-triggered** re-observation/replanning with a scripted policy in the full recovery test. It does not show an autonomous scout dispatch, an ML policy learning online from feedback, a generic colony-wide belief graph, crash-durable evidence, or superiority over scripted play. Frozen MLP choices can now consume the same failure-conditioned report filter, but a matched neural-vs-scripted physical recovery study remains future research.

No LLMs, gradients, science credit, food rewards, social reputation, or emergent Create tech unlocks are authorized by these negative observations.

Follow-ups: verify NBT persistence across deliberate restart and common-prefix rollback; add `REQUEST_REOBSERVATION` to the actual hierarchical autonomous task action space; run matched held-out failure-aware policies with physical receipts, including navigation regression [#181](https://github.com/dylandlr/hearthbound/issues/181).
